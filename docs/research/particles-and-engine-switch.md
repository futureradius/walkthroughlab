# Rebuild the interaction map, keep three.js

Yes, walkthroughlab can have a Prismatiscape-style interaction system, and no, it should not switch to a game engine to get it or to get an editor. The product (spelled **Prismatiscape**, not "Prismaticascape") is not a particle system: it is a small 2D texture simulation that follows the viewer, which foliage, water and particle shaders sample, and every piece of it runs on the project's current `WebGLRenderer` on WebGL2. Buying the licence is cheap ($34.99) but buys little for this purpose: most of the plugin is binary Unreal assets an assistant cannot read from disk, the Fab licence forbids "translating" the code, and the author's free videos already disclose the method in enough detail to re-implement it. The real obstacle is inside the project, not in the technology: the test environment has no vegetation, no instancing and no clock, and ADR 0002 says nothing in an environment can move, so content and pipeline come before interaction. On engines, Unreal has no browser-native target at all, Unity and Godot add a multi-megabyte WASM engine that ADR 0001 was written to avoid, and only PlayCanvas or Babylon.js stay in the same size class, at the cost of rewriting the hand-tuned rendering half of the app. The editor the user wants (lights, wind, instances, reflection probes) is reachable as tooling on the existing stack, estimated by the researchers at one to two weeks per layer. Two honest gaps remain: nobody publishes phone frame rates for these effects, and the project itself has no numeric performance target, so everything below needs measuring on a real phone.

## Prismatiscape is a viewer-following texture simulation, not a particle system

PrismaticaDev describes the plugin as "a locally bound global interaction system using the Niagara Grid 2D, and the output is a render target that can be read in any material or any particle" ([Feature Overview](https://www.youtube.com/watch?v=OgXrpMdpkHA&t=0s)). Its whole output is a handful of textures covering a square around the player: a deform texture whose **RG channels store bend direction and amount** and whose BA channels store a fast-fading velocity that drives jiggle, plus an interaction-bubble texture for large foliage, a surface texture (height and normals for sand, snow, mud), a water texture (ripple height and normals) and a wind texture ([Render Target Overview](https://www.youtube.com/watch?v=oz2T9Aeb330)). Particles are only one consumer: a module samples the wind or input texture at each particle's position and adds it as velocity ([Particle Interaction](https://www.youtube.com/watch?v=fa1YtaA-BW0&t=60s)).

The first video explains the core trick node by node. Instead of an upward-facing scene capture, which he dropped because it "has to set up an entire render pass" ([first video](https://www.youtube.com/watch?v=3VfhvULu2k4&t=60s)), each interactor is an analytic sphere or capsule drawn by distance maths: `mask = saturate(1 - distance(worldXY, centre) / radius)`, multiplied by the shape's velocity so each texel stores a push direction, and gated by comparing the shape's height with a terrain height texture ([first video](https://www.youtube.com/watch?v=3VfhvULu2k4&t=300s)). Wind is advected by itself, using the previous frame's colour to distort the current sample position ([first video](https://www.youtube.com/watch?v=3VfhvULu2k4&t=1500s)); water uses a ripple propagation credited to Ryan Brucks and needs a fixed 60 Hz timestep ([Water Interaction](https://www.youtube.com/watch?v=SBVTrFGU3Xo)). Foliage materials then combine the results with a published recipe: bend equals trample vector plus wind plus a little water normal, with wind and wiggle multiplied by `1 - trampleAmount` so flattened grass stops fluttering ([Foliage Interaction](https://www.youtube.com/watch?v=0LKoLjr3cXU&t=240s)).

The performance reputation rests on design, not benchmarks. There are no CPU traces or texture readbacks, one pass feeds several effects, and simulation resolution is "a flat cost" independent of scene content ([Feature Overview](https://www.youtube.com/watch?v=OgXrpMdpkHA&t=600s)). The only hard figure is a stress test of **2,400 capsules at about 70 FPS** on a Ryzen 3900X with an RTX 2080 Super, with no resolution or baseline stated ([Marketplace launch video](https://www.youtube.com/watch?v=NPssOkSKABs&t=0s)). Default texture resolutions, window size and millisecond costs are never given. The author also lists limits that matter for architecture: it is a 2D projection, so there is no simultaneous multi-storey interaction and no persistent trails once the window moves away ([Feature Overview](https://www.youtube.com/watch?v=OgXrpMdpkHA&t=660s)).

## The licence costs $34.99 and buys almost nothing an assistant can read

Prismatiscape sells for **$34.99 on Gumroad** and on Fab under the Standard License, is maintained (last Fab update 3 June 2026, Unreal Engine 5.3 to 5.7), and its Fab page marks "Use with AI permitted: Yes" ([Gumroad](https://prismaticadev.gumroad.com/l/axvvm); [Fab](https://www.fab.com/listings/be1147e5-65b3-43b2-99a6-a3b2ed0d5748)). The plan to buy it so an AI assistant can study the source fails on three counts, none of them the price.

First, readability. The plugin is built on Niagara Grid2D and Runtime Virtual Textures and requires the Niagara Fluids plugin ([Fab](https://www.fab.com/listings/be1147e5-65b3-43b2-99a6-a3b2ed0d5748)). The researchers' inference is that its Blueprints, materials, material functions and Niagara assets ship as binary `.uasset` files, readable only inside an installed Unreal Engine; only the later C++ core would be plain text, and neither listing confirms that C++ source rather than binaries is included. Second, the licence. The Fab Standard License allows private use and modification, but section 6 says you may not "attempt to reverse engineer, decompile, translate, disassemble, or derive source code or data from the Content", and Unreal plugins may be distributed only inside Unreal-based projects ([Fab EULA](https://www.fab.com/eula)). A line-by-line port of the plugin's shaders to GLSL is plausibly a "translation"; a clean implementation written from an understanding of the method is not, because techniques and channel layouts are ideas rather than protected expression. This is an interpretation, not legal advice. The Gumroad listing states no licence terms at all, so asking PrismaticaDev on his Discord is the free way to settle intent. Third, redundancy. The Unreal-specific parts (Grid2D, virtual textures, parameter collections, pivot painter) must be replaced in three.js anyway, and what remains portable is the concept, which the first video and the eight-video documentation playlist give away ([docs playlist](https://youtube.com/playlist?list=PLUi8nuTUEtTthSUmNHGUYjETYhly0OcsR)).

What the paid source would add is narrow: the exact trample accumulation rule, wind advection constants, the ripple kernel, and how the window scrolls. Each is a short shader tuned by eye. Buying a copy to support the author or to run the demo for reference is reasonable; buying it as an implementation source is not worth the legal exposure it adds over working from the videos.

## The whole effect fits WebGL2; the project's baked light is the real constraint

The same architecture already ships in three.js. Three.js Grassworks, a commercial WebGPU product launched in September 2026, uses an influence map that "moves with the camera", fades over time, and exposes map resolution as the cost dial ([three.js forum](https://discourse.threejs.org/t/i-built-a-real-time-grass-system-for-three-js-webgpu/94175)). The building blocks are standard: two render targets swapped each frame because "the GPU cannot read and write the same texture in a single pass" ([Codrops](https://tympanus.net/codrops/2026/03/23/building-a-dual-scene-fluid-x-ray-reveal-effect-in-three-js/)), and vertex shaders that sample a texture, as Bruno Simon's open-source folio-2025 does for **78,400 grass blades** in one draw call with wind from a shared module ([folio-2025 Grass.js](https://raw.githubusercontent.com/brunosimon/folio-2025/main/sources/Game/World/Grass.js)).

WebGPU is neither needed nor safe to require. Measured WebGPU adapter availability is only **73.6% on Android and 85.4% on iOS** ([web3dsurvey](https://web3dsurvey.com/webgpu)), and the three.js maintainers say compute shaders "are not fully compatible with WebGL 2" ([three.js forum](https://discourse.threejs.org/t/tsl-and-webgl2-vs-webgpu/87974)). An interaction map written as an ordinary fragment-shader feedback pass avoids the issue entirely. The one portability trap is texture format: linear filtering of 32-bit float textures is available on only **50.7% of iOS devices** ([web3dsurvey](https://web3dsurvey.com/webgl2/extensions/OES_texture_float_linear)), while rendering to float or half-float targets is supported on 99.95% of WebGL2 devices ([web3dsurvey](https://web3dsurvey.com/webgl2/extensions/EXT_color_buffer_float)), so the map should be half-float or plain 8-bit.

The project is well placed mechanically. It already drives its own `WebGLRenderTarget`s and `onBeforeCompile` patches for ambient occlusion and glass (`src/occlusion.ts`, `src/n8.ts`, `src/environment.ts`), and the viewer is a ready-made interactor: `advance()` yields a position and floor height every frame, a body radius of 0.4 m, and a top speed of 1.4 m/s, with velocity one subtraction away (`src/motion.ts`, `src/collision.ts`). One interactor moving at walking pace is the cheapest case this technique has. The researchers' order-of-magnitude reasoning, uncited and unmeasured, is that a 256×256 feedback pass is well under 5% of the fragment work the app already does for its main and ambient-occlusion passes.

What is missing is everything around the effect. The test environment is 8,884 triangles of static marble, glass and water with no plants, no instancing, no time uniform and nothing that moves (`public/models/test-environment.glb`, `src/main.ts`). ADR 0002 states the reason outright: "Nothing in an environment can move, since its shadow would stay behind" (`docs/adr/0002-bake-light-with-scripted-blender.md`). An interaction system is therefore downstream of three prior decisions: amending ADR 0002 so that things excluded from the bake may move and are lit live by the sky; adding an instanced-vegetation path to a pipeline whose optimise step currently merges geometry; and making the ambient-occlusion depth pass, which draws the scene with an override material (`src/n8.ts`), apply the same displacement or it will shade the undisplaced shape.

A sensible build order, as proposed in the research notes and resting on engineering judgement rather than cited sources, has four independently shippable steps. Start with global wind on tagged vegetation via `onBeforeCompile`, weighted by a vertex colour or height. Add ambient dust as one stateless draw call wrapped around the camera, with no render targets. Then add the interaction map: the viewer stamps a soft disc at foot level with its velocity, a feedback pass decays it over one to two seconds, and vegetation bends away. Water ripples on the existing `3d_Water` pool are the fourth candidate and the only one needing no new content, though three.js water-ripple guidance was not verified in this research. Known pitfalls, also uncited experience: snap the window to whole texels or the map blurs as the viewer walks, enlarge bounds or disable culling on displaced meshes (folio-2025 sets `frustumCulled = false`), fade the effect at the window edge, and gate all motion behind the `prefers-reduced-motion` setting the project already honours.

## No game engine delivers a phone link without a heavier payload or a bill

The switch question has a clear answer once the hard requirement is restated: a static link that opens fast on old phones, currently about 4.1 MB of content plus roughly 0.25 MB of compressed JavaScript (measured from `public/` and `dist/`).

| Option | Browser delivery | Engine payload (empty project) | Editor | Verdict for walkthroughlab |
|---|---|---|---|---|
| Unreal Engine 5 | Pixel Streaming only; no native web export since 4.24 | None on the client; about one GPU server per viewer | Full | Breaks static hosting and zero running cost |
| Unity 6.6 | Static WebAssembly build; WebGPU off by default | About 8 to 10 MB | Full | Large payload, iOS memory crashes on record |
| Godot 4.7 | Static WebAssembly build, WebGL2 only | About 9 MB gzipped | Full, text scene files | The option ADR 0001 already rejected |
| PlayCanvas | Native web engine | About 1 to 2 MB | Hosted cloud editor | Viable size, but scenes leave the git repository |
| Babylon.js 9 | Native web engine | Not found | Editor v5, node particle editor | Viable, but a full renderer rewrite |
| Needle Engine | three.js runtime (vendor fork) | Not found | Unity or Blender | Closest fit, EUR 49 to 67 per seat per month |

Unreal is the only place Prismatiscape itself runs, and it cannot reach a browser natively: delivery is Pixel Streaming, typically one GPU instance per concurrent user ([Cinevva engine comparison](https://app.cinevva.com/guides/web-game-engines-comparison)). Eagle 3D Streaming prices that from **$0.10 per minute** or $100 per concurrent user per month ([Eagle 3D Streaming](https://www.eagle3dstreaming.com/?p=4179)), so a thousand five-minute visits cost roughly $500 against nothing today. Unity is the strongest conventional candidate: WebGPU left experimental status in Unity 6.6 on 1 September 2026, which lets its GPU particle system run in a browser ([Cinevva news](https://app.cinevva.com/news/2026-09-01-unity-6-6-webgpu-production)). But an empty URP build is almost 10 MB ([Unity Discussions](https://discussions.unity.com/t/a-lot-of-unneeded-stuff-in-webgl-build-how-to-get-rid-of-it/1659235)), users report random crashes on iOS 18 ([Unity Discussions](https://discussions.unity.com/t/webgl-random-crashes-on-ios-18-works-fine-on-ios-18/1627624)), and the compute-based effects are exactly the ones that fall back to nothing on older phones. Godot's web export is still WebGL2 only and its docs still warn that "Safari has several issues with WebGL 2.0 support" ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)). No controlled cross-engine benchmark of time to first frame on phones was found, so these comparisons rest on reported build sizes, not measured load times.

The cost of leaving is small in code and large in tuning. The app is about 1,860 lines of TypeScript, half of it free of three.js (`src/`), so a port to PlayCanvas or Babylon.js is days of rewriting. What does not copy across is the accumulated look: the glass blend, the rule that spares sunlit surfaces from ambient occlusion, and coasting constants tuned by hand on a phone, which took nine of the project's 32 commits. And an engine would not remove the central problem. Moving foliage under baked light, phone fill-rate limits and the absence of compute on WebGL2 follow the project into any engine. It is also telling that the commercial product closest to this brief, Shapespark, is itself a WebGL viewer with baked lightmaps rather than a game-engine export ([Capterra](https://www.capterra.com.au/software/209128/shapespark)).

## The editor the project needs is a week or two of tooling

ADR 0001 names "fine-tuning environments in an editor" as the one reason to revisit the engine choice (`docs/adr/0001-threejs-static-page-over-godot.md`), so the wish is legitimate. It can be met without changing the runtime, because the gap is narrow: the per-environment config file and `?config` panel already handle scalar tuning, and what they cannot express is spatial data such as positions, boxes and placed instances (`src/settings.ts`, `src/tuning.ts`).

Blender, already a scripted dependency, covers most of that through its documented glTF exporter: custom properties export as `extras`, lights export through `KHR_lights_punctual`, "GPU Instances" writes `EXT_mesh_gpu_instancing`, and named vertex colour layers survive export for wind stiffness ([Blender manual](https://docs.blender.org/manual/en/5.0/addons/import_export/scene_gltf2.html)). three.js loads those instances as `InstancedMesh`, and glTF-Transform, which the project already runs, can create them after export with `instance()` ([three.js forum](https://discourse.threejs.org/t/blender-export-instancedmesh-directly/73769); [glTF-Transform](https://gltf-transform.dev/modules/functions/functions/instance)). Since the scene is baked, placed lights are most useful as inputs to the Blender bake rather than as runtime lights. For lighting things that are not lightmapped, such as instanced plants, three.js gained an official diffuse probe volume, `LightProbeGrid`, in r184 in April 2026 with a WebGL version ([three.js docs](https://threejs.org/docs/pages/LightProbeGrid.html)); it is young and its API changed three times by September. Specular reflection probes remain custom work: three.js has no built-in box projection or probe blending, the official example was removed in r132, and the best reference is a React-only helper whose shader would need porting ([three.js forum](https://discourse.threejs.org/t/parallax-correction-from-environment-maps/32692); [drei docs](https://drei.docs.pmnd.rs/misc/use-box-projected-env)).

The visual editors in the three.js ecosystem do not apply, because Triplex edits React Three Fiber components and Threlte Studio requires Svelte ([Triplex docs](https://triplex.dev/docs/get-started); [Threlte docs](https://threlte.xyz/docs/reference/studio/getting-started)). Needle Engine is the one product offering Blender-side authoring of lightmaps and reflection probes over a three.js runtime, but its web component owns the canvas and it uses a fork of three.js ([Needle docs](https://engine.needle.tools/docs/three/)), so adopting it means moving the app into Needle, not adding an editor to the app.

The researchers' own effort estimates, for one developer with an AI assistant and not drawn from any published source, are below. No published figures exist for any of these.

| Layer | Estimate | What it gives |
|---|---|---|
| Extend config file and panel (wind, scatter density), dev-only save endpoint | 1 to 3 days | Non-spatial tuning without copy and paste |
| Sidecar scene file with schema (probes, wind zones, scatter rules, lights) | 3 to 5 days | Diffable spatial data an assistant can edit |
| Blender-extras convention with validation in `npm run optimize` | 3 to 7 days | Placement in a real 3D editor |
| In-app edit mode with `TransformControls`, writing the sidecar file | 1 to 2 weeks | Placement in the real renderer |
| Specular probes with box projection | 1 to 2 weeks | Believable reflections on glass and metal |
| Runtime scatter plus wind shader for instanced vegetation | 1 to 2 weeks | Vegetation with small downloads |
| Adopt Needle Engine | 3 to 6+ weeks plus subscription | A full editor, effectively an engine switch |

Two caveats shape this path. Rhino remains the modelling tool and authors currently never open Blender, so a Blender convention is a workflow change for the human, and whether Rhino can export per-object properties to glTF was not checked. And the editor layer is the small part: the runtime features behind it (probe shader, wind shader, instancing and culling) are what an engine supplies ready-made and what this project would build itself.

## Conclusion

Both questions turn out to be about the same thing, and it is neither Unreal nor particles. Prismatiscape's appeal is one cheap texture that many shaders read, and that design is renderer-agnostic and free to study. The project's friction is that everything spatial lives in Rhino or in source constants. A sidecar scene file serves both: it is where wind zones, scatter surfaces and probe boxes would be declared, it is what an in-browser gizmo or a Blender script would write, and it is the format an AI assistant edits best, which is the advantage a game engine's binary scenes would take away.

The decision that actually gates progress is ADR 0002, not the engine. Until the project defines how unbaked, moving things are lit, wind, foliage and interaction have nowhere to live in any engine. The second gate is measurement: with no reference phone, no target frame rate and no public mobile benchmarks for these effects, the first prototype should be judged with `?fps` on the oldest phone at hand. The condition that should reopen the engine question is specific: if environments come to need many placed dynamic lights and blended reflection probes, or if the audience shifts from public phone links to a few clients on good hardware, PlayCanvas or Unity becomes worth costing. Neither is the case at three days and one environment.
